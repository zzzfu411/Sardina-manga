# Sardina 0.3.0 体验、功能与代码逻辑复审

审计日期：2026-09-26。代码基线：`299d21e35927b7ef526525a9a7ef46b6fe5c683a`。本次重新检查当前实现，并用独立浏览器和合成响应复现异常场景。没有修改应用源码或用户日常浏览器中的书架、下载和偏好；本轮交付为审计报告与复现证据。

**结论：主体功能已经连通，上一轮的性能和数据保护修复也仍然有效。但“请求成功→内容可读”“在线目录→本地下载”“自动保存→用户删除”“后台任务→当前阅读”之间的约束尚未完全打通。下一轮应先修复这些交界处，再扩展推荐和阅读功能。**

复审发现 12 组具体问题。其中 10 组有浏览器或可重复的逻辑探针证据；取消收藏缺口由代码确认；测试诊断缺口由本次实际失败和检查入口实现共同确认。下面另外列出的推荐、搜索和跨设备方向属于产品能力建设，不混作已复现的运行故障。

**R01 · 坏图会被反复当作缓存命中，重试没有重新取图**

复现：源第一次返回 HTTP 200、`image/png`，但内容无法解码；后续图片请求本可返回正确 PNG。打开阅读器后连续点击两次“重试此页”。结果：章节清单请求从 1 次变成 3 次，图片请求仍然只有 1 次，页面保持错误状态。不是上游持续失败，而是没有发起新的图片请求。

原因：[image-loader.js:25](../web/image-loader.js#L25) 在解码前缓存 Blob；命中缓存直接返回。[reader.js:475](../web/reader.js#L475) 先刷新清单，清单地址不变时又把错误页变回待加载并立即入队，随后提前返回，没走增加重试编号的路径；同一坏 Blob 再次被使用。网络图解码失败也没有反馈给加载器使缓存失效。

建议：给加载器增加精确的失效或强制重取接口；将“刷新章节地址”和“重新获取图片字节”分开。当前页重试必须清理对应的失败缓存，并保持同页请求合并和并发限制。下载流程已经有解码校验，不能把这个问题误写成下载也完全不校验图片。

验收：在地址完全不变的情况下，首次返回坏图、第二次返回好图，只点击一次重试即可显示；确认真正发起第二次取图，且已成功的其他页面不重下。

证据：[product-probes.json](../output/playwright/audit-20260926/scenarios/product-probes.json) 中 `corruptRetry`；[错误页截图](../output/playwright/audit-20260926/scenarios/corrupt-retry.png)。

**R02 · 空清单进入成功缓存，整章重试在缓存期限内无效**

复现：适配器先返回空数组，下一次调用应返回有效图片。连续调用章节 API 两次，均报“这个源未返回章节图片”，实际上游只调用一次。显式增加 `refresh: true` 才取得正确结果。与此同时，章节健康记录显示 `ok`。

原因：[server.py:270](../server.py#L270) 在缓存与健康记录完成后才判断清单为空，因此空数组缓存 60 秒。[reader.js:598](../web/reader.js#L598) 的“重试本章”未要求刷新。

建议：在加载函数内部验证章节结果，再进入成功缓存和健康记录。保留“合法空搜索”与“不可用空章节”的区别；用户显式重试应有清晰的缓存绕过语义。

验收：第一次空清单不进入成功缓存、不记章节成功；第二次普通重试可恢复。继续保留同 key 并发合并、错误不会污染其他请求等既有约束。

证据：[backend-probes.json](../output/audit-20260926/backend-probes.json) 中 `emptyChapterCache`。这是注入适配器异常返回的边界测试，未据此推断所有源都经常返回空清单。

**R03 · 下载保存成功，但最新在线目录能使本地章节失去入口**

复现：完整下载第 1 话，保留其 Blob；将共享目录从“第 1、2 话”更新为仅有“第 2 话”，模拟源站删章或调整目录。再次进入第 1 话链接，提示“原章节已不在当前目录中，请重新选择”，阅读器不打开。数据库仍显示该章 `complete: true`，本地图片仍存在。

原因：[download-store.js:78](../web/download-store.js#L78) 覆盖同书共享目录；`hydrate` 在共享目录存在时不会补上下载记录自身的章节。[app.js:337](../web/app.js#L337) 必须先在该目录找到章节才允许进入阅读。下载管理打开完整记录也会经过这一路径。

建议：将最新在线目录和已保存章节集合建模为两个独立事实。完整下载可按下载记录直接阅读；目录展示可以标明“本地保存”，但不冒充源站仍有该章节。前后章导航遵循当前可确定的序列，不用名称相似度猜测替代章。

验收：在线目录移除当前章、离线目录过期、从下载管理或深链接打开三种情况下，已下载页都能正常显示；本地入口不依赖重新请求图片。

证据：[product-probes.json](../output/playwright/audit-20260926/scenarios/product-probes.json) 中 `removedDownloadedChapter`；[现场截图](../output/playwright/audit-20260926/scenarios/downloaded-chapter-missing.png)。

**R04 · 旧阅读会话的自动保存可以撤销另一标签的删除**

复现：标签 A 显示漫画首张；标签 B 移除该漫画。A 接收存储事件后书架计数已降为 0。此时 A 不翻页，仅点击“返回”，计数恢复为 1；等待存储完成后，B 也读到新记录，刷新 A 仍为 1。

原因：[reader.js:230](../web/reader.js#L230) 退出会保存进度，关闭过程也会保存。[app.js:41](../web/app.js#L41) 在记录已不存在时仍自动建立阅读记录；[library-store.js:58](../web/library-store.js#L58) 只比较写入时钟，新自动保存晚于删除标记，故被视为有效新建。已有“旧写入不能复活删除”的保护，不能处理“旧会话新产生的写入”。

建议：区分显式收藏/重新打开和既有会话自动保存，为阅读会话保留删除代次或开始时的版本；同时避免未改变位置时重复提交。用户之后主动重新阅读仍可按产品规则新建阅读历史。

验收：删除后关闭旧阅读器、隐藏标签、触发 `pagehide` 都不会重新入架；主动重新打开是另一种明确操作，并有独立用例。

证据：[ux-probes.json](../output/playwright/audit-20260926/scenarios/ux-probes.json) 中 `crossTabRemoval`。该记录已等候写入并刷新复核，排除了仅是计数闪动的解释。

**R05 · 推荐偏好会被另一标签的普通曝光事件覆盖**

复现：两个推荐反馈实例读取同一存储。A 标记“不感兴趣”并关闭个性化；B 随后记录一张卡片曝光。持久化数据从“不感兴趣 1 本、个性化关闭”变成“0 本、个性化开启”。A 内存仍保留自己的设置，新建实例却读取到丢失后的结果。

原因：[recommendations-feedback.js:36](../web/recommendations-feedback.js#L36) 每次把初始化时读取的整份状态覆写回同一个键，缺少字段合并和协调；[app.js:498](../web/app.js#L498) 的跨标签同步只处理书架键。点击、曝光、阅读统计也共享这一写入方式。

建议：为明确偏好、作品排除、曝光和统计分别设计合并规则。利用 Web Locks 串行读改写，并监听相应存储事件；撤销与清空需要代次或删除标记，不能简单取集合并集，统计也不能简单取最大值而丢失并发事件。

验收：两个标签交错执行曝光、打开、关闭偏好、排除和撤销后得到一致结果；普通曝光绝不能改变显式个性化开关。

证据：[model-probes.json](../output/audit-20260926/model-probes.json)。这是使用同一存储的两个模块实例确定性复现，未把它描述成真实两窗口推荐 UI 测试。

**R06 · 阅读器内部有优先级，服务端仍会被后台图片占满**

复现：让 8 个后台封面占据服务端图片槽位，再请求一张当前阅读页；该阅读页自身的模拟获取可立即完成，却等待 5.005 秒后得到“图片请求较多，请稍后重试”。

原因：[server.py:119](../server.py#L119) 和 [server.py:132](../server.py#L132) 对所有图片使用同一个 8 路信号量，并设置 5 秒等待。前端阅读/下载加载器有优先级，但封面 `<img>`、其他标签和服务端等待均不在这个优先队列内。限制总并发解决了资源上限，却没有保证前台及时获得资源。

建议：端到端区分当前页、阅读预取、显式下载、封面；为当前页保留服务额度，并限制后台占用，兼顾源站级并发。应通过队列和取消处理，不依靠把所有超时加长。

验收：受控慢封面和后台下载同时进行时，当前页仍能进入服务；后台不会无限饿死；同一图片复用、总请求上限和取消行为仍正确。上线速度结论需另测真实网络，不能把这个合成压力用例当作日常平均等待时间。

证据：[backend-probes.json](../output/audit-20260926/backend-probes.json) 中 `foregroundStarvation`。

**R07 · 推荐和源健康的“成功/失败”还没与读者看到的结果对齐**

有三条相互印证的证据：R02 的空清单被记作章节成功；某源正文图失败后，一次封面图片成功会把该源的 `image` 状态重新覆盖为 `ok`；R01 从推荐打开后一直坏图，统计为 `opens: 1`、`readingStarts: 0`，但 `openFailures: 0`。

原因：[server.py:137](../server.py#L137) 把代理的封面与正文都记录为 `image`；[source_health.py:42](../client/source_health.py#L42) 保留的是最后一次结果。[reader.js:425](../web/reader.js#L425) 的解码错误没有进入推荐失败回调；回调主要接在整章加载失败。排序则直接读取这些健康信息：[recommendations-ranking.js:69](../web/recommendations-ranking.js#L69)。

建议：先明确事件契约：目录有效、清单有效、首张解码成功、当前页失败、重试恢复、持续阅读。区分封面与正文，保留近期成功/失败窗口和样本量；未知不算成功。推荐会话失败与恢复分别记录，并限定每会话去重，避免重复点击重试把一个故障计成很多次。

验收：封面成功不能抹去近期正文失败；HTTP 成功但内容不可读能进入相应失败指标；恢复后能记录恢复而保留故障事实。推荐相关性实验必须建立在这些定义稳定之后。

证据：上述 backend 与 product 探针的 `coverOverwritesReadingHealth`、`emptyChapterCache`、`corruptRetry.metrics`。

**R08 · 关闭界面继续增加浏览器历史，返回会重开刚关闭的内容**

复现路径为“发现→详情→阅读→返回详情→关闭详情”。历史长度从阅读时的 4 增加至 6。浏览器返回一次重新打开详情，再返回一次重新打开阅读器。

原因：[app.js:72](../web/app.js#L72) 的路由方法默认 `pushState`，[app.js:300](../web/app.js#L300) 关闭详情和 [app.js:431](../web/app.js#L431) 退出阅读均再次压入记录。页面导航和弹层关闭没有共享历史所有权模型。

建议：记录弹层由哪条历史记录打开；有应用内父记录时回退，无父记录的深链接使用明确的替换回退路径。换章是否作为历史步骤也应在规格中统一，避免简单把所有 push 改为 replace 破坏正常后退。

验收：普通打开/关闭、直接深链接、连续切章、浏览器前进后退都返回符合预期的背景页、查询与位置，不循环弹回已经关闭的弹层。

证据：product 探针 `historyLoop` 的路径、历史长度与对话框状态。

**R09 · 书架空页面给出的恢复操作并不总能恢复**

第一处：仅有自动阅读记录，勾选“只看收藏”后为空。点击“查看全部”，仍为“显示 0 / 1 本”，“只看收藏”仍勾选，提示还错误地写成“还没有标为‘全部’的漫画”。原因是 [app.js:416](../web/app.js#L416) 清除了查询、更新和状态筛选，却漏了收藏筛选。

第二处：在发现页打开空书架，点击“去找漫画”，只关闭书架；路由仍是 `/discover`，试图聚焦的头部搜索框实际隐藏。原因是 [app.js:415](../web/app.js#L415) 仅按首页是否隐藏来挑选输入框，没有处理发现页同样隐藏搜索的情况。

建议：将“清除全部筛选”和“进入搜索并聚焦”设为复用动作；空状态文案根据实际生效的筛选生成。

验收：所有筛选组合下“查看全部”恢复书架总数；从首页、发现页和搜索页进入空书架后，“去找漫画”都提供可见、可输入的搜索入口。

证据：product 探针 `emptyRecovery`、UX 探针 `emptyShelfSearch`；[截图](../output/playwright/audit-20260926/scenarios/shelf-empty.png)。

**R10 · 收藏和阅读历史在数据层已拆开，在操作层仍未闭合**

代码确认：[app.js:377](../web/app.js#L377) 已收藏时直接返回，不能改为未收藏；书架唯一移除操作 [app.js:159](../web/app.js#L159) 会删除整本记录。用户想取消收藏但保留阅读位置和逐章状态时，没有直接操作。

建议：让收藏可以切换，取消收藏保留进度；删除阅读历史另有明确动作。对移出记录提供短时撤销，可以减少误操作损失，无须增加繁琐确认弹窗。

验收：收藏→阅读→取消收藏后，“只看收藏”中消失，阅读历史及继续位置仍存在；再次收藏不重置进度；明确移除后可按设计撤销。

**R11 · 数据写入已优化，界面仍按总规模重建**

本次在真实 Chromium 中装入 1,000 本书、每本 20 条章节状态。打开书架同步处理 69.3 ms，观察到一个 69 ms 长任务，书架创建 1,000 张卡片、约 12,000 个子节点。输入仍匹配全部书的查询时，每次同步处理约 17.5–18.1 ms，至两个动画帧后约 75.5–83.7 ms。测试书没有封面网络开销，不能外推为实际用户 p95。

2,000 章目录实测创建 6,022 个详情子节点；进入阅读后，尚未展开的阅读器目录也已经创建 2,000 个条目、4,000 个子节点。这次目录观察没有长任务，不能把它写成已证实的严重卡顿，但它说明初始成本随总章数增长、重复建设隐藏内容。

原因：[app.js:399](../web/app.js#L399) 的书架渲染逐本创建完整卡片，查询输入直接触发全量重建；[app.js:388](../web/app.js#L388) 和 [reader.js:549](../web/reader.js#L549) 对目录采用相同模式。

建议：大书架采用窗口渲染或渐进分页；目录首次展开再创建，搜索保留全数据索引；更新单本状态时局部更新。优化过程中保留键盘焦点、滚动位置、辅助技术可达性和筛选总数。

验收：以 100 / 1,000 / 更大书架规模分别测交互与 DOM 数量，并加入受限 CPU 场景；视口外节点数量有明确上限；未打开目录不产生全量条目；单本状态变化不重建整书架。性能预算应以指定设备测量定义，不能沿用存储层 1.2 ms 作为界面流畅证明。

证据：[ux-probes.json](../output/playwright/audit-20260926/scenarios/ux-probes.json) 的 `largeShelf`；[catalog-probe.json](../output/playwright/audit-20260926/scenarios/catalog-probe.json)。

**R12 · 有回归入口，但失败时留下的现场不足以解释原因**

本次第一次固定阅读回归等待 `.ry-reader-page[data-state="loaded"]` 超时；同一脚本有多个该等待点，无法从异常得知失败发生在离线恢复还是长章切换。其后增加临时阶段诊断的运行通过，第二次固定三组浏览器运行也通过。首次日志另有资源连接重置，但缺少完整现场，不能断言是产品根因。

原因：[scripts/check.py:35](../scripts/check.py#L35) 失败后立即抛出，最后的 `summary.json` 不会写出；浏览器退出前没有统一捕获失败阶段、截图、DOM、请求失败和 trace。现有浏览器回归集中在 Chromium，手机体验仍主要由桌面视口代替。

建议：为步骤命名；在失败时保留阶段、控制台、失败请求、截图和 trace，最后始终输出成功与失败汇总。复跑可辅助定位，但不能抹掉首次失败。随后加入关键移动浏览器和连续长图场景，CI 持续记录结果；目前仅能确认本地运行，不能宣称托管 CI 已通过。

验收：故意制造一张图片失败，能从产物直接找到其章节、阶段、请求结果与屏幕；失败退出码保持非零；前三组某组失败时仍有汇总文件。

证据：[首次阅读回归日志](../output/playwright/audit-20260926/baseline/reader-search.log)、[复验结果](../output/playwright/audit-20260926/browser-recheck/summary.json)。

**从软件工程上，应先补清楚的规格**

| 用户意图 | 必须成立的系统约束 | 对应问题 |
|---|---|---|
| “重试后给我一次新的恢复机会” | 错误内容不得持续命中成功缓存；重试要改变导致失败的状态 | R01、R02 |
| “我已下载，就应该能打开本地那一章” | 本地资产的可达性不取决于源站最新目录 | R03 |
| “我的删除和偏好应被尊重” | 被动保存不能推翻更晚的显式操作；并发字段有独立合并规则 | R04、R05 |
| “先让我看到当前页” | 资源优先级从前端到服务端一致，前台有可用额度 | R06 |
| “可读性和统计要符合真实体验” | 接收字节、有效清单、可解码、持续阅读是不同事件 | R07 |
| “返回、清空筛选、取消收藏应符合字面含义” | 路由、弹层、筛选与书架操作使用一致的状态转换 | R08–R10 |
| “书多后仍然流畅，出错后能查清” | 用完整用户路径的性能预算和失败证据验收 | R11、R12 |

代码层不需要为了这些问题重写为另一套框架。更有收益的调整是：为缓存入口建立可消费的数据契约；分开远端目录与本地资产；给自动保存和用户命令明确操作类型；将路由、详情与书架交互从 `app.js` 的共享状态中逐步分离。阅读加载保持单一会话所有权，缓存、解码和失败反馈用明确接口连接。每次拆分围绕一条上述约束和对应复现推进，保留现有数据格式与迁移保护。

**建议的下一轮执行顺序**

1. 先处理 R01–R05，同时补上 R12 的最低失败记录能力。交付标准是坏图可恢复、空清单不污染缓存、本地已下载章可达、跨标签明确操作不丢失。把本次复现改为固定的行为回归，避免仅断言内部函数被调用。
2. 再处理 R06–R07：统一请求分类、前台预算与可读性事件。用慢封面、坏图、过期清单和恢复后的好图组成故障矩阵；测首张可读时间、当前页等待和重试恢复率，保留未检查状态。
3. 整理 R08–R11 的交互：路由返回规格、完整筛选重置、可逆收藏、书架与目录渐进渲染。手机视口之外增加受限 CPU、长目录键盘导航与真实设备样本。
4. 最后推进推荐与搜索评估、受预算控制的下一章预取、备份迁移等功能。只有资料与事件可靠后，排序效果比较才有意义；新能力各自先定义范围及验收，不把它们塞入一次大改。

本次没有发现足够证据支持“整体必须推倒重写”，也没有确认普遍的数据文件损坏。当前最值得投入的是上述可复现的恢复与状态一致性问题。没有改动或发布应用代码；审计结束时本地服务仍在 `http://127.0.0.1:8765/` 运行。
