# Sardina 全面审查与优化建议

审查日期：2026-09-25（Asia/Shanghai）。对象：当前目录内 Sardina manga 0.2.0 的 Python 服务、源适配器与原生 JavaScript 前端。交付性质：审查报告、复现证据与后续执行建议。本轮仅新增审查资料并启动本地服务，未修改产品实现。

**结论**

Sardina 已具备可用的聚合搜索、发现、阅读、书架和章节下载流程。现在最需要投入的是第三方数据的信任边界、下载恢复、持续源维护与阅读性能。推荐也还有很大空间，但先补元数据和评价方法，才有条件调整算法。

本轮优先级最高的两项是：源站脚本存在直接交给本机 Node 执行的回退路径；未完成下载保留的图片地址过期后，阅读器重试无法恢复。推荐与视觉优化应建立在这些问题修复之后。

**方法与证据边界**

- 阅读关键实现、接口契约及历史交付记录；运行当前全套自动测试。
- 使用独立 Playwright 会话和合成数据，复现过期图片地址、下载清空、旧目录、长章图片驻留、下载实例竞争；不清空日常浏览器的书架。
- 对 25 个注册源各做一次“三月的狮子”搜索；读取一批真实推荐；强制刷新《五等分的花嫁》漫画巴士样本章节的图片列表，并完整解码首图。
- 本地无破坏性样本验证解码器的代码执行行为；样本不联网、不读取个人文件、不执行文件写入。
- 检查真实搜索页面、320/393 像素阅读页面和键盘焦点。未做真实手机长时间内存测试、所有浏览器兼容测试、全部 25 源逐章阅读测试，也未进行外部攻击或渗透测试。
- 在线数字是当前网络环境的一次抽样，不是长期成功率、平均时延或 p95。推荐统计仅对应首批 6 个列表，不能外推全部来源。

**F01 · P1 · 第三方章节脚本可进入本机执行环境**

定位：[解码回退](../client/dm5_family.py#L209)、[源站响应进入解码器](../client/dm5_family.py#L476)。纯解析器失败后，`unpack()` 会调用 `node -e`，用 `eval(m[1])` 执行源站响应中的表达式。15 秒超时只限制运行时间，不限制文件或进程能力。

证据：本地样本返回预设标记，并确认能访问 `node:fs.writeFileSync`。它没有实际写文件，但已足以证明表达式在有 Node 内置能力的环境中运行。若响应被源站或传输链路篡改，可影响运行 Sardina 的本机用户权限范围。没有发现实际入侵证据。

同一传输层还有放大因素：[DM5 Session](../client/dm5_family.py#L304) 和 [native 请求](../client/native_sources.py#L61) 在证书校验失败时自动降级为不校验证书；DM5 Session 还会保留这个不安全 opener。

建议：删除任意脚本执行回退，扩充受限数据解析器，对未知格式明确报错。保留固定可信解码代码与远端数据的分离；移除自动 TLS 降级，通过正确 CA 配置解决证书问题。不要把简单套一层 JavaScript `vm` 当作完整安全边界。

验收：普通已知格式仍可解析；包含 Node 内置模块访问、函数调用或格式异常的合成响应只能被拒绝，不能执行；证书失败只返回可解释错误，不发起未验证的第二次请求。

**F02 · P1 · 部分下载会把阅读器锁在过期图片地址上**

定位：[优先采用下载清单](../web/reader.js#L570)、[单页重试](../web/reader.js#L436)。只要下载记录包含 URL，即使尚未下载完，阅读器也不再请求章节图片列表。单页重试只给本地代理 URL 加重试参数，源站地址仍旧不变。

复现：2 页章节仅保存第 1 页；旧地址返回 403，章节接口可返回新地址。第 1 页本地打开正常，第 2 页及再次重试都失败；章节接口调用数为 0，旧地址请求 2 次。

建议：分开管理本地已保存页面与在线图片地址。缺页遇到可恢复错误时，对该章合并发起一次 `refresh: true`，更新待加载地址后重试；限制刷新次数，避免无限重试。已完整下载的章节保持离线可读。

验收：上述 2 页用例无需删除下载即可打开第 2 页；第 1 页不重下；网络不可用时已存页面仍能读；章节切换后的迟到刷新不能覆盖新章节。

**F03 · P2 · 图片签名刷新会清空已下载页面**

定位：[下载清单变更处理](../web/download-store.js#L57)。非完整下载只要任意 URL 字符串变化，就删除该章全部 Blob、生成新 generation 并清零进度。

复现：只把两张图片 URL 的 `signature=expired` 改为 `signature=fresh`，已存页数从 1 变成 0，第 1 页 Blob 消失。真正的章节内容变更需要隔离旧数据，但签名变化与内容变化现在无法区分。

建议：由各源提供可信的页身份/内容版本，再决定能否复用已存页面。身份不明确时保留旧版本直至新版本准备成功，不要先清空。不能简单删除所有查询参数：有些参数本身就是图片身份。

验收：同页签名变化保留已验证的页面；页面顺序或内容真正变化时不会错误复用；刷新失败、空间不足或取消操作不会提前丢弃原有可读页面。

**F04 · P2 · 下载目录快照覆盖了在线新目录**

定位：[选择本地详情](../web/app.js#L300)、[下载详情快照](../web/downloads.js#L81)。继续阅读或深链接打开已下载章节时直接使用下载时保存的全书目录，缺少后台更新和目录刷新入口；本地快照的优先级甚至高于 `refreshCatalog`。

复现：下载时只有第 1 话，服务端已有第 2 话；在线刷新阅读页面后仍显示 1 章，“下一章”禁用，详情接口刷新次数为 0。

建议：本地内容立即打开，同时独立刷新在线目录；提供明确的刷新目录操作。更新目录不得移动当前页，也不能把离线快照误记为已检查过的新目录。

验收：离线仍能打开第 1 话；在线恢复后出现第 2 话；本地已下载状态和当前阅读位置不变。

**F05 · P2 · 源迁移已发生，缺少持续健康记录**

定位：[可可漫画注册和地址校验](../client/apk_vomic_html.py#L20)、[静态源目录](../client/source_catalog.py#L14)。本轮可可漫画搜索失败，提示“漫画地址与所选源不匹配”。旧搜索入口实际返回 301，Location 为 `https://keke2026.com/search?...`。本轮只确认跳转，没有将目标域名视作已验证的新阅读源。

当前“已接入”表示有适配器，接口也明确 `liveAvailabilityChecked: false`，这点是诚实的；产品层面仍缺少上次搜索/目录/首图成功时间、失败类别和近期延迟。用户只能在搜索后发现某源失效。

建议：先核验目标站作品身份、目录、图片与权限，再维护允许的域名别名和旧链接迁移。建立按搜索、目录、阅读、榜单划分的能力与健康记录；优先从实际用户请求被动记录，主动探测采用小样本和退避。保留全部源入口，让用户明确选择重试，不因暂时失败静默删除源。

验收：迁移源通过搜索→目录→公开章节→首图解码；旧书架记录可关联稳定源内 ID；健康状态标注时间和能力，不将空搜索结果、验证码或权限限制混为“坏源”。

**F06 · P2 · 手机搜索页把筛选器放在阅读目标之前**

定位：[逐源渲染筛选按钮](../web/app.js#L225)。393×852 页面里，源筛选区域高 427 px；首部作品从 y=729 开始，第一个章节按钮在 y=1039。横向没有溢出，但用户需要先越过大量不相关的源状态才能阅读。

另一个小问题是状态文字同时出现“25 / 25 个源已完成”和“部分源未完成”。实际含义是 25 个请求结束，其中 1 个失败。

建议：默认显示“全部、常用、有结果、失败”摘要与当前选择；全部 25 源放在可展开筛选面板。作品内默认保留已选择/常用源，其他源按需展开；同源多个条目展示版本、章节量等可用依据。保留现有纸张与手绘品牌，优先改信息顺序。

验收：393×852 下首部精确命中作品与一个阅读入口在首屏可见；全部源仍可键盘访问；筛选后焦点稳定；失败数与已响应数文案一致。

**F07 · P2 · 图片请求有边界，读过的图片驻留没有边界**

定位：[图片完成后保留 img](../web/reader.js#L396)、[仅结束章节时清理](../web/reader.js#L237)。24 MiB 是加载器 Blob 缓存限制，不是阅读器总内存上限。

复现：在逐页模式读完 60 页，DOM 仍保留 60 个带 src 的已加载图片，仅 1 页可见。浏览器是否回收解码缓存依具体实现而定，本轮没有测量真实设备 RSS，也没有证据声称已经发生内存崩溃。

建议：保留章节位置和图片比例，把图像资源限制在当前页附近的窗口；远处页面保留占位尺寸，必要时释放图片源。逐页模式先实现较小窗口，再处理连续长图模式，避免滚动跳动。下载 Blob 与显示资源生命周期分离。

验收：200–500 页测试中，遍历后的活动图像资源不随已读页数无限增长；回翻、缩放和恢复进度正确；真实手机验证峰值内存与帧时间，再确定窗口大小。

**F08 · P2 · 缓存命中仍可能被无关慢请求拖住**

定位：[Cache.get](../server.py#L65)。缓存分成 64 把条带锁，读取命中结果前先拿锁，慢请求执行 `load()` 的整个过程都持有该锁。不同 key 碰到同一条带会互相阻塞。

复现：key 64 已缓存；key 0 的模拟加载占住同一条带。缓存命中请求被延迟约 355 ms，直到无关加载放行。这个数字来自人为阻塞实验，用于证明机制，不是线上平均延迟。

建议：先在短锁内检查有效缓存；未命中才进入真正按 key 合并的进行中请求表。为源站元数据与图片设置共享的在途请求/并发预算。当前前端读取+下载的 4 并发只约束一个页面；源响应在后端读取完之前，浏览器取消不会自动终止已经开始的上游读取。

验收：无关慢 key 不影响有效命中；同 key 冷请求只加载一次；异常会释放进行中状态；多标签阅读与下载时服务端总请求数受控。

**F09 · P2 · 保存一本的阅读位置仍扫描整份书架**

定位：[阅读进度触发保存](../web/app.js#L40)、[整库比较、复制和读取](../web/library-store.js#L70)。底层虽按书写记录，但 `save(books)` 每次全量比较、克隆，写后再读取并校验全书架。应用还刷新继续阅读和推荐画像。

浏览器合成基准（每本 20 条逐章状态，7 次保存中位数，存储用内存 Map，不含真实 localStorage I/O）：

| 书架规模 | save 同步部分 | 完整 save 等待 |
|---|---:|---:|
| 100 本 | 0.7 ms | 2.2 ms |
| 500 本 | 3.7 ms | 11.2 ms |
| 1,000 本 | 7.0 ms | 21.4 ms |

建议：提供 `updateProgress(bookKey, progress)` 和记录级通知；阅读位置变化不重建全部推荐画像。保留独立字段时钟、删除标记和跨标签合并规则。达到实际容量需求后再迁移 IndexedDB，而非一次推翻已验证的存储协议。

验收：只改一书只持久化一条记录，不全量解析其余书架；1,000 本真实存储测量同时给出主线程长任务；现有旧备份、删除保护和跨标签测试继续通过。

**F10 · P2 · 多标签可重复下载同一章节**

定位：[下载任务表](../web/download-model.js#L28)。队列与并发控制存在于当前页面内存中，下载没有书架那样的跨标签协调。

复现：两个独立 manager 共用真实 IndexedDB 下载同一 2 页章节，产生 4 次模拟网络加载；两边都报告完成。页面存储计数仍正确，问题是重复流量和重复工作。这里模拟的是两个独立 manager，而非声称已做两台设备测试。

建议：按下载任务取得跨标签锁或带过期时间的任务租约，通过 BroadcastChannel 同步进度。关闭标签页后可被其他标签接管；取消一个阅读消费者不能取消另一标签明确请求的下载。

验收：同时开始时每页最多一个有效下载；拥有任务的标签关闭后可恢复；另一标签删除任务后旧任务不能复活。

**F11 · P2 · 下载元数据重复且空间展示不完整**

定位：[每章保存整本目录](../web/download-store.js#L47)、[下载列表全量读取](../web/download-store.js#L89)、[进度变化时刷新列表](../web/downloads.js#L22)。每个下载任务复制整本 `chapters`，每次列表刷新又读取所有记录。

复现：100 个任务，每本目录 1,000 章，共保存 100,000 个目录条目；元数据 JSON 约 6.23 MB，记录中的图片 bytes 总和仍为 0；一次 `list()` 约 19.3 ms。JSON 大小不是 IndexedDB 精确磁盘占用，但说明界面“已用空间”未计入这类元数据。

建议：拆成作品目录表、章节任务表、页面表，目录按书和版本共享；列表只取摘要，变更单行增量刷新。将应用图片预算、浏览器实际配额和持久存储状态分开显示。保留失败重试与显式删除机制。

验收：100 个下载只存一份对应目录版本；进度更新不读全列表；配额不足、用户拒绝持久存储、页面被回收时给出准确状态；迁移已有下载不丢页。

**F12 · P2 · 推荐最大的限制是内容数据不足**

定位：[候选列表字段](../client/recommendations.py#L33)、[内容特征规则](../web/recommendations-ranking.js#L5)。首批 143 条候选：有作者 89 条（62.2%），有简介 9 条（6.3%），有 tags/genres 0 条，能提取现有内容线索 7 条（4.9%），有封面地址 143 条。这里确认的是封面地址存在，并非 143 张封面均已逐张解码。

这意味着大部分候选无法通过题材相似度得到个性化分数，只能依赖作者、列表类型、来源顺序和多样性规则。只改权重，或者引入向量模型，也无法凭空补出缺失信息。

建议按顺序做：规范作者与类型字段；缓存用户实际打开作品的元数据；对候选少量、受控地补充详情；保留语言和版本身份；将已知阅读能力与近期健康作为推荐质量信号。不要为 143 本同时拉取全部目录，也不要将未知可读性标成已验证可读。

验收：每批记录作者/简介/标签覆盖率和缺失原因；能对同一用户明确展示有证据的个性化差异；推荐打开失败单独计入质量指标；来源、理由和封面恢复机制保留。

**F13 · P3 · 推荐权重需要质量评估，曝光抑制过于绝对**

定位：[画像权重](../web/recommendations-ranking.js#L21)、[排序比较](../web/recommendations-ranking.js#L73)、[反馈期限与指标](../web/recommendations-feedback.js#L4)。曝光记录保留 28 天，排序先比较“是否曝光”，再考虑相关度。

合成用例中，相关分 0.8 的未曝光作品排在相关分 10 的已曝光作品前。想读收藏的权重 4，也高于已读收藏的 3；这些是现有产品规则，不是数学计算错误。它们缺少真实阅读效果证据，可能让“换一批”很新鲜，但兴趣匹配下降。

建议：曝光使用有时间衰减的有限惩罚，设多样性配额和可解释回退；区分明确收藏、有效阅读、读完、返回继续读，以及用户主动表示不喜欢。初期继续使用可解释本地规则，不急于构建协同过滤系统。

验收：固定候选集和测试画像，检查相关性、多样性、版本去重、已读排除和曝光恢复；记录推荐打开后是否成功进入阅读、是否继续阅读。没有用户反馈样本前，不宣称“推荐准确率提升了多少”。

**F14 · P2 · 自动测试数量够用，持续验收入口仍不完整**

当前目录不是 Git 仓库，也未找到项目 CI 工作流。已有 28 个 Python 测试文件、17 个 JavaScript 测试文件，`uv.lock` 存在。关键浏览器验收和真实 IndexedDB 用例主要保存在历史 `output/` 脚本中；`npm test` 只运行模型测试，因此无法捕获本轮发现的多个接线问题。

建议：将有意义的浏览器恢复用例纳入固定回归入口；建立受版本控制的源码、测试和迁移记录；把大 APK、生成物、网络探测输出与可发布代码分开。在线源探测与离线回归分开运行，前者报告外部变动，后者稳定阻止代码回归。

验收：一个明确命令可运行离线单元、HTTP、真实 IndexedDB 和核心浏览器恢复测试；失败保留最少复现材料；对版本发布可指出变更、迁移方案和回退方式。不要只以测试条数作为发布质量标准。

**已经做得比较稳的部分**

- 当前搜索样本将简繁体及“3月/三月”聚成一部作品，11 源仍能单独选择；未知作者与冲突作者处理有针对性测试。
- 阅读/下载共享图片加载器具有当前页优先、请求合并、消费者独立取消、超时和 Blob 缓存边界。
- 下载页面与页数统计在同一事务提交，generation 防止迟到任务覆盖已删除记录；完整下载可读和部分下载恢复是已有基础。
- 书架具有版本化备份、字段合并、逐章状态、删除标记和写入失败提示，适合渐进改造。
- 本机 HTTP 服务有源地址允许列表、重定向校验、Host/Origin 校验、CSP、体积限制等保护；F01 指出的是具体残留回退，不能由这些保护自动抵消。
- 页面无额外构建要求，当前体量适合继续保持模块化原生实现。更换前端框架本身不会解决上述问题。
