# COLAMANGA APK 解包独立复核

日期：2026-09-21。范围是上一轮使用的官网下载 App 2.1.1，以及本地 COLAMANGA / onemanhua 的 4 份插件文件；不是对全部 174 个 APK 的完整反编译声明。

**结论：这 5 份 APK 的完整性、解压结果、Manifest 和 DEX 提取通过独立校验；上一轮对 Flutter AOT 的 ASCII 字符串扫描存在噪声，不能称为完整的接口反编译。** 两个配置 URL 的字节与位置正确，但正常游客请求方法、参数和调用链尚未恢复。

## 校验方法与结果

| 层次 | 本次重新检查 | 结果 |
| --- | --- | --- |
| APK 文件 | 逐个重算大小、SHA-256 | 5 份与原记录一致，实际为 3 个不同构建 |
| ZIP | 全量解压读取 CRC、大小、重复名、路径及目录结构 | 2,017 个条目通过 |
| DEX | 文件长度、头部、SHA-1、Adler32 | 9 个 DEX 通过，含重复插件内的 DEX |
| 原生库 | ELF64 / AArch64、程序段与节边界 | 17 个 ELF 文件通过 |
| APK 签名 | Google `apksig 8.7.3` 的 `ApkVerifier` | 5 个全部 `verified=true`；App v2/v3，插件 v1/v2 |
| 独立解压 | Python ZIP 与系统 `unzip -p` 逐字节对照 | 8 个选定关键成员一致 |

上述计数中，ZIP / DEX / ELF 全量检查按 5 个输入文件计算；Androguard 在 SHA-256 去重后解析 3 个构建，包含 7 个 DEX，并保留另外两份文件的逐字节同一性证明。

完整性校验脚本另经 11 个合成正反例检查，覆盖 CRC 损坏、DEX 摘要和长度错误、ELF 段越界与 ABI 错配、ZIP 重名及路径越界，均按预期通过或检出错误。见 [脚本自检结果](../output/apk-revalidation-20260921/integrity-selftest-results.json)。

签名校验说明现有 APK 的签名与所覆盖数据一致；本轮没有使用可信发布者证书基线做身份比对。插件 v1 校验提示 Gradle 的 `META-INF` 元数据未由 v1 保护，同时 v2 全包校验通过；原始提示保存在结果中，没有忽略或删除。

证据：[完整性与签名结果](../output/apk-revalidation-20260921/integrity-results.json)、[Androguard 对照](../output/apk-revalidation-20260921/parser-crosscheck.json)、[AOT 字节核对](../output/apk-revalidation-20260921/semantic-byte-verification.json)。

## 确实发现的问题

上一轮直接扫描 ELF 的连续可打印 ASCII 字节，无法天然识别 Dart 快照中的字符串边界，造成两类误差：

1. `/subscriptionV` 含疑似粘连字节。局部长度前缀与 `/subscription` 相符，尾部 `V` 更可能属于后续记录；不能直接把原值作为路由名称。
2. `/mhD` 等 8 个短斜杠串没有通过相同的局部边界检查，应保留为原始扫描命中，不列入有边界依据的候选字符串。

另外，`ComicDetail {`、`  mangaName: "` 等展示文本片段不能当作 JSON 字段契约。即使独立字符串名存在，也仍需实际调用和响应确认其含义。

这里的“长度前缀一致”只是局部格式检查，不是完成了 Dart 对象池和快照反序列化。本轮已冻结旧提取结果，后续修正仍能回溯到原始记录，避免将修正后的文件冒充上一轮的输入。

修正已写回上一轮的 `apk-research-official-static.json`、`apk-research-summary.json` 与 `audit.json`：完整保留 89 条原始路径扫描命中；另列 81 条局部边界筛选后的候选，逐项标记 `httpEndpointVerified=false`；8 条疑似噪声与 20 条展示片段分别保存。摘要中的 14 个字段名补充独立字节位置，其中 `packageName` 的独立候选位于 **361584**；它们仍未与 JSON 请求或响应契约绑定。

见 [修正明细](../output/apk-revalidation-20260921/semantic-corrections.json) 与 [实际写回记录](../output/apk-revalidation-20260921/corrections-applied.json)。未删除原始证据，也没有因此增加或启用漫画源。

## 哪些协议结论仍然成立

- `https://apibase.colamanga.com/getAppBaseData` 在 `libapp.so` 的字节偏移 **322154**。
- `https://apibase.acloudmerge.com/getAppBaseData` 在字节偏移 **191473**。
- 两个完整 URL、核心候选路径和游客界面文案确实存在，未因本次校验失效。
- `libapp.so` 是 Flutter/Dart AOT，只有快照级导出符号，缺少普通函数符号及调试映射。线性反汇编能解析 AArch64 指令，但尚未把具体 URL 与 HTTP 方法、参数、请求头和响应解析建立关联。

因此，上一轮的普通 GET 403 是一次真实请求结果，**不能证明它就是 App 的正确请求方式，也不能证明游客接口不可用**。本轮没有把未还原的协议认定为永久不可接入；COLAMANGA 保持未启用，是因为搜索 → 完整目录 → 页列表 → 真实图片的实际验收尚未完成。

## 复现

从项目根目录运行。解析工具安装在独立临时环境，未修改云漫的运行依赖；所有步骤均不安装或执行 APK。

```bash
# ZIP、DEX、ELF 全量检查与标准 APK 签名验证，工具 JAR 已保存在审计目录
.venv/bin/python output/apk-revalidation-20260921/integrity-check.py
.venv/bin/python output/apk-revalidation-20260921/integrity-selftest.py

# 单独环境中的第二套 Android 解析器
uv venv --python .venv/bin/python --cache-dir /private/tmp/revyunman-apk-audit-cache /private/tmp/revyunman-apk-audit-20260921
uv pip install --python /private/tmp/revyunman-apk-audit-20260921/bin/python --cache-dir /private/tmp/revyunman-apk-audit-cache -r output/apk-revalidation-20260921/parser-requirements.txt
/private/tmp/revyunman-apk-audit-20260921/bin/python scripts/verify_colamanga_apks.py

# 对冻结的上一轮提取结果逐字节复核，并保存反汇编样本
.venv/bin/python output/apk-revalidation-20260921/semantic-audit.py

# 从已保存的审计结果重放标注修正（只更新提取 JSON，不改 APK 或源注册）
.venv/bin/python output/apk-revalidation-20260921/apply-evidence-corrections.py
```

工具来源：[Androguard](https://pypi.org/project/androguard/4.1.4/)、[Google Maven apksig 8.7.3](https://dl.google.com/dl/android/maven2/com/android/tools/build/apksig/8.7.3/apksig-8.7.3.pom)。APK 原始文件与云漫启用源列表没有改动。
