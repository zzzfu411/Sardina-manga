# 云漫：成熟漫画软件对标与质量审计

审计日期：2026-09-22。对象为当前工作区的云漫本地版。目的：明确具体质量问题、产品能力差距和下一阶段顺序，尤其是推荐系统。本轮只生成审计与复现材料，未修改业务代码、用户书架或运行配置。

**后续实施状态（2026-09-22）：** F01–F10 已在后续优化轮次修复并建立回归，推荐与阅读体验也已迭代，见[执行计划](2026-09-22_优化执行计划.md)与[交付记录](2026-09-22_优化交付记录.md)。下文保留审计时的事实、行号与原始复现结果，不代表修复后仍有同一缺陷。

**核心判断：云漫已经具备可用的多源搜索与阅读基础，但作品身份、章节完整性、持久化和推荐反馈尚未形成一致的数据契约。接下来优先保护收藏与阅读连续性，再让推荐利用真实的作品和阅读数据。**

三个并行审计分别检查推荐、搜索与源适配、阅读器与书架；主任务复核证据并查阅成熟产品官方文档。下文明确区分「已复现缺陷」「现有设计的体验代价」「尚未实现的能力」。受控故障复现不代表相应源站现在正在发生故障；本轮也没有重新下载全源漫画验证可用率。

**3. 与成熟软件对比：分别借鉴适合云漫的能力**

这些产品的定位不同，不能把所有功能混成一张必须全做的清单。尤其是商业内容平台拥有统一作品库和大量用户行为，聚合阅读器需要先解决跨源数据不一致。

| 产品类型与代表 | 官方资料确认的能力 | 云漫适合借鉴的部分 |
|---|---|---|
| 多源阅读器：Mihon | 迁移来源时可选择转移数据；支持每部作品的阅读模式、自动备份和基于阅读状态／更新间隔的智能更新 | 换源带进度、按作品保存阅读设置、完整备份、减少无效追更请求 |
| 私有漫画库：Komga | 用户独立进度、未读数量；四种阅读方向／布局、手势、适宽／适高／原尺寸、双页与缩略图 | 清晰的章节已读模型、手机缩放、页漫与条漫分别优化 |
| 私有内容库：Kavita | 题材、语言、状态、人物、进度等元数据筛选；可保存为 Smart Filter 并用于个人首页栏目 | 「完结＋某题材＋未读」这样的发现入口，保存用户筛选，减少翻找 |
| 商业漫画平台：WEBTOON | 公开说明使用阅读历史、阅读模式、偏好标签、作品交互等推荐信号；用户可排除不想看的作品 | 可跳过的偏好设置、阅读反馈、负反馈和可解释推荐；模型规模应适应云漫的数据量 |

对标来源：[Mihon 换源迁移](https://mihon.app/docs/guides/source-migration)、[阅读设置](https://mihon.app/docs/guides/reader-settings)、[备份](https://mihon.app/docs/guides/backups)、[智能更新](https://mihon.app/docs/faq/updates/smart)；[Komga 阅读进度](https://komga.org/docs/guides/read-progress/)与[漫画阅读器](https://komga.org/docs/guides/webreader-divina/)；[Kavita 元数据筛选](https://wiki.kavitareader.com/guides/features/filtering/)与[首页自定义](https://wiki.kavitareader.com/guides/features/customization/)；[WEBTOON 2026 年 9 月公开推荐说明](https://m.webtoons.com/en/notice/detail?noticeNo=3751)。这些页面支持相应功能或输入信号，不能据此推断其未公开的完整模型和权重。

Mihon 的官方备份文档也明确区分备份搬运和实时跨设备同步；因此云漫下一步可以先把恢复做好，再按实际使用需求实现同步。无需把账号登录作为所有改进的前置条件。

**4. 推荐系统的真实现状**

目前是「漫本人气榜＋漫画柜更新交错取最多 24 本，再排除书架、每批展示 12 本」。[配置与取数](../client/recommendations.py#L17)和[前端选择](../web/recommendations-model.js#L90)均未根据阅读偏好排序。

| 当前机制 | 实际限制 | 优化方向 |
|---|---|---|
| 固定两源、最多 24 本 | 新增 23 个发现源不会自动进入推荐；24 本中收藏 23 本后只剩 1 本，后续候选不会补入 | 展示批量与候选池容量分离；共享发现能力，有界补召回 |
| 按列表位置交错 | 喜欢日漫、国漫、完结或某作者，不影响推荐顺序 | 显式偏好＋本地阅读反馈＋内容相似度 |
| 12 本顺序轮换 | 24 本正常池中，第三批完全回到第一批 | 记录真实可见曝光；有未见候选时优先展示；耗尽时补充或明确说明 |
| 没有正常卡片的兴趣反馈 | 封面失败的「换一本」只是图片容错，不能表达不喜欢 | 增加轻量「不感兴趣／已读」、撤销、减少某类内容 |
| 收藏后保留当前批次 | 这是现有测试固定的稳定位置策略，并非偶发缓存失灵；但卡片不显示已收藏状态 | 当前卡标记「已加入书架」，下一批／新会话按作品身份排除 |
| 推荐和发现各自取数、缓存 | 先看漫本榜再开推荐会再次请求漫本；冷请求等待慢源；客户端载入后可长期复用旧池 | 共享每个列表的缓存与请求合并；先显示已有内容，再按软过期时间更新 |
| 无推荐效果记录 | 测试能证明数量与轮换正确，不能证明推荐有用 | 建立最少的本地事件与离线回放基线 |

现有推荐可追溯源站、隔离来源失败、图片懒加载、刷新失败保留卡片，这些应保留。推荐样本小是早期实现取舍，但现在已形成明显的内容覆盖瓶颈。

**5. 适合当前云漫的推荐方案**

建议第一版采用**内容推荐与明确规则的组合**。协同过滤依赖用户与作品之间的多用户反馈矩阵；当前本地单用户没有这类数据。作者、题材、简介和本人的阅读反馈已经可以支持有用的排序。参考 [Google 协同过滤说明](https://developers.google.com/machine-learning/recommendation/collaborative/basics)；以下具体设计为本项目建议，不是上述漫画软件的公开算法配方。

```mermaid
flowchart LR
    A[多源热门与更新] --> B[作品身份与版本核对]
    B --> C[有界候选池与来源状态]
    D[本地偏好与阅读反馈] --> E[内容与规则排序]
    C --> E
    E --> F[去重与多样性调整]
    F --> G[推荐卡片和真实理由]
    G --> D
```

这一拆分与推荐系统常见的候选生成、评分和重排结构一致。结构依据见 [Google 推荐系统概览](https://developers.google.com/machine-learning/recommendation/overview/types)；下面的候选规模与比例均为待验证的初始设计。

1. **先让候选有可靠身份。** 最小记录应区分作品、版本、来源条目。保留主标题／别名、作者角色、语言、页漫／条漫、题材、连载状态、来源证据和时间。字段未知就保留未知；不把抓取时间当作品更新时间，也不按一次失败认定整部作品不可读。
2. **扩大召回，控制请求成本。** 从已验证且适合用户语言的列表选少量来源，轮换覆盖其余来源；初始可试 100–300 本元数据候选。热门、近期更新、同作者、相似题材各有独立召回理由。补足过滤后的候选，复用发现缓存，不读取章节正文来生成推荐。
3. **解决首次使用。** 可跳过地选择几个题材、语言、完结偏好和已有喜欢的作品。跳过时提供分布较丰富的热门精选；初始池没有个性化依据时，文案只说明真实榜单来源。
4. **建立可靠偏好信号。** 「明确喜欢／想读」、多次主动续读、章节完成分别记录；一次搜索、打开详情或短暂试读只作为弱信号。当前阅读会自动入架，不能把所有书架条目直接当强烈喜欢。后台停留不能算有效阅读，翻到最后一页也不能自动证明读完全部内容。
5. **先做可解释打分。** 作者与标签相似度、简介 TF-IDF 等轻量文本特征、源内归一化热度、真实更新时效和探索项可以组成初始分数。负反馈、近期曝光用于降权；作品存在多个来源时优先选择适合语言／版本且近期成功的入口。不同来源的点击量和不同周期榜单不能直接相加；共享内容库的品牌源不能重复放大同作热度。
6. **在最终列表控制重复。** 一批中同一作品最多一张，相关来源收在卡片内；保留原作、重制、彩版等有证据的版本区别。对过度集中于单一题材、作者的列表做多样性调整，并保留小部分探索内容。比例先通过使用反馈调整，不把固定百分比写成经过验证的最佳参数。
7. **让用户可理解、可纠正。** 理由可以是「同作者」「与你喜欢的悬疑题材相近」「来自某源本周榜」。卡片提供不感兴趣与撤销；在详情或读完一章后展示少量相关作品。曝光／偏好数据默认本地保存，可关闭和清空。

算法升级顺序应由效果决定：规则＋内容相似度建立基线后，再评估语义向量是否确实改善别名／简介匹配；有足够真实多用户数据和明确同步需求后，再考虑协同过滤。大模型可作为可选的离线标签辅助，结果需有来源或人工确认；不应在每次开推荐页时临时编造漫画或补造元数据。

**6. 推荐之前与同时需要补的基础模型**

建议采用以下概念边界，可先以小型本地数据库实现，不要求复杂服务拆分：

| 实体 | 要解决的问题 |
|---|---|
| Work（作品） | 推荐去重、收藏与用户偏好的稳定身份；不要只用标题字符串 |
| Edition（版本） | 原作／重制、语言、彩版、条漫与页漫等区别；缺证据时保守分开 |
| SourceEntry（来源条目） | 源内作品 ID、规范地址、旧域名／旧地址别名、封面和目录入口 |
| ReadingSequence（阅读序列） | 语言、卷话或翻译版本的前后章关系；不要把不同语义的 group 一刀切处理 |
| Progress（进度） | 逐章已读、最近位置和来源页面偏移分开保存；跨源迁移不能照抄页码 |
| SourceObservation（来源状态） | 最近成功／失败、阶段、错误类型与时间；已注册、已验证和实时可用分开 |

先完成源内 ID 与旧 URL 映射，修复可以确定的重复；跨源关联结合作者角色、版本、语言和外部 ID。对《一拳超人》不能因为标题相同就将 ONE 原作与村田重制版直接合并。现有五组作者字符串说明字段粒度不统一，不能证明五组都错误。

「换源查找」目前只重新搜索标题。后续迁移应展示候选版本和目录差异，用章／卷／标题匹配产生可核对的目标；不确定时让用户选章。不同源分图、裁切不同，页内进度应保守恢复，原进度保留到新来源打开成功。

持久化可按本地产品采用 SQLite 保存书架、条目映射、检查点和最少行为事件，浏览器保留视图状态；也可先用 IndexedDB 改善浏览器记录存储，但它仍有浏览器／端口边界。无论选哪种方案，都需要记录级更新、格式版本、迁移与可恢复备份。当前书架整数组写回且没有跨标签页同步，存在旧快照覆盖新记录的风险；这项为代码推导，本轮未做真实多标签页复现。

**7. 阅读、追更和发现体验的改进方向**

- **读完、未读与更新通知分开。** 当前每本只保留最后章节和页位置，缺少逐章已读集合；整本「已读」是人工分类。打开目录确认更新通知，不等于已经读完新增章节。增加逐章状态之后，才能可靠提供「继续下一未读章」、未读数与有效阅读反馈。
- **手机用实际可用的尺寸与手势。** 当前宽度滑杆为 480–1,200px，393px 视口下三种宽度都会被压到 393px，控件不能改变显示。改为适宽／整页／原比例，辅以图片内缩放、平移、双击和可配置翻页热区。浏览器原生缩放目前没有被禁止，不能说手机完全不能放大。
- **按作品保存阅读设置。** 页漫与条漫的模式、方向和缩放需求不同，支持单书覆盖全局默认。优先复用现有模式切换与保位逻辑。
- **长章节先量，再做窗口化。** 当前网络请求有界，但一次创建所有页节点、逐帧遍历页面且已解码图片没有应用层离屏淘汰。先测 180／500 页和 1,000 章目录的交互、内存与长任务，再引入保留高度的窗口、图片预算和增量计数。本轮未测出真实卡顿，不把这项写成已发生的崩溃。
- **追更从手动走向可控的自动检查。** 先做「打开应用且上次检查过期」时检查常读连载书，允许关闭；再利用更新规律减少对完结／长期未读作品的无效请求。保留手动强制检查、取消和逐书错误处理。不要仅凭未读数就永久跳过用户明确关注的作品。
- **预取按来源能力决定。** 当前逐页只取当前页是对计次图片源的保守设计。普通图片可以试可选的相邻页预取，计次／配额源继续显式请求。预取量、已解码图片预算和退到后台的行为需要一起定义。
- **增加可保存的发现筛选。** 题材、语言、完结、页漫／条漫、阅读状态适合做少量常用筛选；有元数据后再提供个人书单和 Smart Filter。首页继续保持搜索与继续阅读为主，复杂选项收在发现页和设置中。
- **离线与同步放在后续独立阶段。** 应用级离线需要下载队列、章节清单、配额、清理与恢复；HTTP 图片缓存不等于离线书库。同步需要逐记录冲突规则，不能简单把整个 localStorage 文件互相覆盖。登录只是身份入口，无法代替这些数据设计。

**8. 源可靠性与工程维护**

建议统一接口中的 `completeness`（完整／部分／未知）、`expectedCount`、`retrievedCount`、权限提示与结构化错误码。至少区分无结果、访问挑战、超时、配额耗尽、解析变化和部分返回。F03–F06 共同暴露了完整性、权限与错误状态缺少统一契约；其中 `unavailableReason` 混用具体导致了 F06 的追更问题。

将现有真实请求产生的成功率、耗时与失败阶段记录到本地，分别看搜索、目录、章节元数据、图片。先用这些被动证据改进默认来源选择，避免为健康检测批量请求正文。常用源现在只影响请求顺序，默认作品入口仍是硬编码优先级；后续可综合用户偏好、已选语言／版本和近期故障，并保持用户主动选择不被后台响应改掉。

搜索还需要声明返回范围：部分适配器只取 30／50 条或前 2／3 页，却没有统一 `hasMore`／`truncated` 字段。应该允许在真实分页证据下追加搜索，并显示还有未取结果。保持全部已启用源的覆盖，不能用无提示关闭源换取速度。

现有服务缓存有界且按 key 合并请求，但主要在进程内；推荐还绕过了发现列表的缓存。可先建立共享元数据缓存和全局／每源预算。浏览器取消会阻止旧结果更新页面，服务端已经发起的普通阻塞请求仍可能工作到结束；多标签页情况下要测总在途量，再决定是否需要更深入的取消或调度改造。没有必要以文件行数为由重写架构。

**9. 验收标准应覆盖「正确」和「有用」**

现有测试保护了很多交互与解析行为，但有些测试也固定了早期取舍，例如推荐两批循环、带任何权限提示都拒绝追更。测试数量不能替代正确的验收条件。

| 目标 | 建议验收方式 |
|---|---|
| 数据不丢 | 任意合法导出能导回；增加第 301 本不静默删除旧书；迁移前后进度可核对；持久化失败有明确状态 |
| 阅读完整 | 可信总数不满足时不得完整成功；重复／缺页／重叠分页故障注入；当前语言末章不跨序列 |
| 搜索可信 | 正常空页与挑战页严格分开；真实别名命中进主区；按语言／版本标注一组人工核对样本 |
| 推荐身份正确 | 同名异作均保留、确定同作聚合、旧地址连续、版本不混；作者未知不得消除已知冲突 |
| 推荐能持续发现 | 有未曝光候选时不循环重复；前 24 本入架后仍能补足下一批；负反馈可撤销且刷新后有效 |
| 推荐有帮助 | 先建立固定候选和几份兴趣档案，比对当前交错策略与新排序；真实使用看曝光到收藏／主动续读／有效阅读，同时观察负反馈和重复率 |
| 性能有依据 | 分别记录首个可用搜索结果、首张可读图片、推荐首批、失败率与 p95；在同网络／设备／缓存条件下比较，不把本轮模拟延迟当线上性能数据 |

有足够反馈后可引入 Recall@K／NDCG 等离线排序指标，并按时间切分数据避免用未来行为评估过去推荐。当前单用户阶段，人工审定的身份样本、几个偏好明显不同的档案和真实「愿不愿意继续读」反馈更容易形成可靠基线。曝光应在卡片真正可见时记录；封面网络失败和后台停留都不能被误当成兴趣反馈。

**10. 建议迭代顺序**

| 阶段 | 主要交付 | 完成条件 |
|---|---|---|
| A：可靠性修复 | F01–F07；同名去重和英文别名契约也可并行修 | 备份往返、301 本、缺页、重叠目录、挑战页、部分锁定目录、多语言末章用例全部通过；旧记录可恢复 |
| B：身份与存储 | 源内稳定 ID、旧 URL 迁移、最小 Work／Edition／SourceEntry、逐章状态与持久化 | 老书架无损迁移，同作入口可关联，不同版本不会自动误并 |
| C：推荐 v1 | 共享发现候选池、补召回、本地偏好、可解释内容排序、曝光去重、负反馈 | 固定对照样本效果优于旧轮换；收藏大量候选后仍可发现新书；请求预算有界 |
| D：长期阅读体验 | 手机尺寸／缩放、单书设置、章节序列、可控自动追更、长章性能 | 常见手机尺寸和长章节完成实测；阅读与更新状态一致，来源故障可理解 |
| E：按需求增加 | 离线、跨设备同步、外部追踪服务、更高级语义推荐 | 前四阶段稳定，存在明确使用场景和效果基线 |

近期最值得投入的是 A 与 B 的最小闭环，再推进 C。推荐池扩展、曝光去重和清楚的反馈可以较早交付；跨源迁移和持久身份必须与旧书架兼容一起设计。大规模协同过滤、每次请求都调用大模型、社交评论系统、复杂运营后台暂时没有相应数据或产品需求依据。
